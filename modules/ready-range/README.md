# Ready Range｜點餐到可取餐的等候區間

午餐還有幾張單在做，店長想知道有多少客人在目標時間內等到餐。這個 Python 工具讀取禾日食堂的分站出單檔，把仍在等候與已取消的訂單一併列入。它會回答「至少幾張、至多幾張準時」，也能分別看內用與自取。

## 重跑五張午餐單

使用 Python 3.10 以上。命令列只需標準函式庫。將四份合成範例寫入新目錄後依時間順序讀取。

```sh
python example.py lunch
python ready.py --target-seconds 40 lunch/1.json lunch/2.json lunch/3.json lunch/4.json
python ready.py --target-seconds 40 --mode table lunch/1.json lunch/2.json lunch/3.json lunch/4.json
python -m unittest -v
```

| 取餐號 | 最後已知狀態 | 下單到可取餐 | 40 秒內可取餐 |
| --- | --- | --- | --- |
| 1 | 已交餐 | 0–40 秒 | 確定達標 |
| 2 | 可取餐 | 10–70 秒 | 尚無法判定 |
| 3 | 製作中 | 至少 70 秒 | 確定未達標 |
| 4 | 可取餐 | 40–100 秒 | 尚無法判定 |
| 5 | 已取消 | 不會出餐 | 確定未達標 |

五張單中，至少一張、至多三張能在 40 秒內取餐。中位數介於 40 與 100 秒。第 90 百分位取排序後第 5 張，因為有一張已取消，這組訂單的第 90 百分位無法在有限時間內達到。

## 比較各付款方式的等候時間

先依上方指令產生四份午餐班快照，再加入同一間店的收據。範例附五張餐單中的四張收據，只保留配對需要的欄位。

```sh
python ready.py --target-seconds 40 lunch/1.json lunch/2.json lunch/3.json lunch/4.json --receipts examples/lunch-receipts.json
```

| 訂單所選付款方式 | 觀察張數 | 40 秒內可取餐的張數 | 從快照能確定的結果 |
| --- | ---: | --- | --- |
| LINE Pay（示範） | 2 | 1 | 一張準時，一張製作中且已超時。 |
| 全支付（示範） | 1 | 0–1 | 可取餐時間介於 10 至 70 秒。 |
| 現場付款 | 1 | 0 | 接單前取消。 |
| 缺少收據 | 1 | 0–1 | 可取餐時間介於 40 至 100 秒。 |

`--receipts` 可重複指定檔案，接受店員以有權限的帳號取得的 `GET /api/kitchen` JSON 陣列，或單張 `GET /api/ticket` JSON。店員的「下載試算收據」提供餐點金額，缺少本分析所需的付款欄位。收據與快照必須來自同一家店。程式核對取餐號、建立時間及內用或自取，再從收據取得付款方式與環境。同一餐單在不同時間匯出可重複提供。若識別資料、支付方式或環境相互矛盾，指令會指出取餐號並中止。

`paymentBreakdown` 列出有收據的訂單數（`matched`）、缺收據的訂單數（`missing`），以及只有收據、從未出現在輸入快照中的訂單數（`receiptOnly`）。最後一種沒有出餐觀察值，只計覆蓋情形。可用 `--mode table` 或 `--mode pickup` 限定範圍。每組分別計算準時數和等候時間百分位；缺收據的群組以 `null` 表示。示範、測試與正式金流各自成組，金額、卡號、桌號及備註皆不進入報表。分組描述的是下單至可取餐的時間，包含廚房排隊與製作，無法據此判定金流處理速度。

## 如何解讀時間

- 報表涵蓋至少在一份輸入檔出現過的訂單。若匯出間隔很長，期間建立並離開保留視窗的單可能從未出現。時間從建立訂單算起，含線上付款與等候接單。
- 同一家店依序完整匯出，前一次下載結束後才開始下一次，且伺服器時鐘穩定。輸入檔應為店員端完整的 `/api/kitchen/stations` 回應。等待時間試算用的製作中清單會篩掉其他狀態，不能用來重建這項指標。
- 服務先讀取資料庫，再寫入匯出時間。某張單本次仍在製作，只能確定它在**前一次匯出時刻**尚未可取餐。首次看到可取餐或已完成，則以本次匯出時刻作為上界。兩個事件可能落在同一毫秒，判定準時包含恰好達標。
- 分站檔保留所有未結案單與取餐號最大的 20 張結案單。若製作中的單消失，而且 20 張結案單的取餐號都比它大，可以推知它已經過可取餐。若最後僅看到等待接單，則仍有取消的可能。工具會拒絕無法由保留規則解釋的消失或狀態倒退。
- JSON 的 `earliestMs`、`latestMs` 以毫秒表示。下界為 `null` 表示該單確定不會出餐，上界為 `null` 表示無法保證有限的等候時間。百分位採排序後第 ⌈訂單數 × 比例⌉ 張，分別用上下界求值。空群組回傳零張與空界限。
- 預設報表列出取餐號、內用或自取、狀態與時間界限。提供收據才會增加付款方式與環境。原始出單檔可能含桌號及顧客備註，範例皆為合成資料。

## 串接點餐與付款

CI 在 Windows 與 Ubuntu 啟動固定版本的禾日食堂 Worker 與暫存 D1，從內用與自取入口送八張單。LINE Pay、全支付、街口支付、悠遊付、Pi 拍錢包、全盈+PAY 與信用卡各完成一筆示範付款，逐筆核對付款前後的接單權限；現場付款單在接單前取消。三次讀取廚房分站資料後，程式核對六張已可取餐、一張仍在製作與一張已取消。驗證使用本機示範金流。[點餐平台原始碼](../../README.md) · [整合測試](demo.mjs)

在儲存庫根目錄執行 `npm ci --include=optional` 後，可從本模組目錄執行 `node demo.mjs ../..`。
