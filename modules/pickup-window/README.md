# Pickup Window｜分站製作與取餐時間估算

午餐尖峰，客人想多點一碗親子丼和三杯煎茶。熱台有兩個鍋位，飲品台有一個工作位。這個 Node.js 工具讀取禾日食堂的分站出單檔，讓店員看到已接餐單的完成區間，也能先估一張新餐單要等多久。程式只讀取檔案，在本機執行。

## 試算一張新單

使用 Node.js 22 或更新版本。指令和估算模組只用標準函式庫。

```sh
node cli.mjs examples/stations.json examples/kitchen.json --cart examples/cart.json
```

範例快照時間是台灣中午 12:00。17 號單有三碗親子丼、兩杯煎茶，18 號單有兩份唐揚雞。19 號單還在等店員接單。估算採用店家的示範工時。

| 情境 | 熱台完成 | 飲品台完成 | 整單可取餐 |
| --- | --- | --- | --- |
| 17 號單 | 12:08–12:10 | 12:01–12:01:30 | 12:08–12:10 |
| 再加一碗親子丼、三杯煎茶 | 12:11–12:14 | 12:03–12:04:30 | **12:11–12:14** |

如果店員已做完一碗，另一碗正在鍋裡、還需 45–60 秒，可在同一份快照補上進度。新餐單的估算會提前到 **12:07:45–12:10**。

```sh
node cli.mjs examples/stations.json examples/kitchen.json --cart examples/cart.json --progress examples/progress.json
```

## 接上自己的廚房

1. 在禾日食堂的店員接單台按「下載分站出單檔」，將第一個引數換成下載的檔案。只有狀態為 `preparing` 的餐單會排入工作站。使用者試算的新餐單會排在這些工作之後。
2. 在 `kitchen.json` 設定每站可同時製作的批數。每道料理指定工作站、一次可作的份數，以及每批最短和最長秒數。範例時間是合成值，店家可代入現場量測結果。
3. 需要更新已動工的餐單時，在 `progress.json` 填寫原快照的 `capturedAt`、餐單 ID、餐點 ID、已完成份數和每個製作中批次的份數與剩餘秒數。空出的工作位可接新批次。未提供進度的餐點從完整批次開始估算。
4. 輸出 JSON 的 `orders` 對應既有餐單，`quote` 對應試算餐單。`seconds` 從快照時間起算，`readyAt` 使用 UTC，`stations` 可用來找出哪一站決定取餐時間。試算不會送單。輸出只保留編號與估算，原始匯出檔可能包含桌號與備註。

## 排序與估算條件

各站平行作業。站內依訂單建立時間、訂單編號、餐點 ID 排序；同一道菜依批量拆開，每批交給最早空出的工作位。已下鍋的批次先佔位，不同餐單分開製作，不跨單湊一批。各批次按最短及最長工時各排一次，每張餐單取各站最後一批完成的時間。當批次順序與站點容量固定，延長工時只會讓排序後的工作位可用時間持平或延後，因此兩次排程給出此模型的上下界。

結果對應匯出當下。店員插單、缺料、跨站共用人力或改變出餐順序，都需要更新資料與估算。這個區間描述上述條件下的廚房製作時間，未包含外送路程。

## 驗證

```sh
node --test estimate.test.mjs
```

獨立的逐秒模擬器枚舉六個批次、每批三種工時的全部 **729** 種組合，逐單核對所有完成時間都在估算內，最快與最慢結果恰好等於兩端。其餘測試涵蓋正在製作的批次、同時空位、已完成數量、過期進度、暫未接單與指令錯誤。

CI 另以固定版本的禾日食堂啟動本機 Worker 和 D1，實際送出三張訂單。兩張接單，一張全支付訂單等候付款。透過店員端點取得快照後呼叫同一個 CLI。當第一張單出餐，新單的估算由 11–14 分鐘降至 4–5 分鐘。可用下列指令重跑。[估算模組](estimate.mjs) · [窮舉測試](estimate.test.mjs) · [Worker 整合演練](worker-demo.mjs)

```sh
npm ci --prefix ../.. --include=optional
node worker-demo.mjs ../..
```

本專案使用 AI 輔助開發。所有展示結果來自合成餐單。
